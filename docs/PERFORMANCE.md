# 轻量化设计与资源测量

TraceTime优先保证计时准确、托盘常驻和本地隐私，再减少不需要的计算、分配与文件。本文记录0.8.1的轻量化优化和与0.8.0的受控对照结果。

## 已落实的优化

| 路径 | 0.8.1行为 |
| --- | --- |
| 启动到托盘 | 延迟读取概览和加载应用图标，第一次打开窗口时再加载 |
| 隐藏或最小化 | 暂停概览/规则列表/日历等视图刷新和资源采样；计时、额度检查及休息提醒继续 |
| 每日时间线收起 | 不构造全天图表、小时切片和明细视图；收起后释放这些派生对象的界面引用，展开时恢复完整内容 |
| 概览排行刷新 | 应用顺序未变时复用已有行和控件，只通知改变的值；筛选或排序改变时正常重建 |
| 全天汇总与画刷 | 每个全天快照只生成一次完整汇总；复用固定的冻结调色板画刷 |
| 前台识别 | 复用类名/进程路径缓冲区，遇长路径再扩容；仍按当前前台进程实际查询，不依靠可能复用的PID长期缓存 |
| Windows x64包 | 明确按win-x64发布，仅携带所需SQLite原生库；框架依赖包继续使用已安装的.NET桌面运行时 |

前台事件与1秒兜底采样、常规5秒保存/提醒检查仍保留。没有降低计时采样频率，没有强制GC或裁剪工作集，也没有新增常驻服务、网络轮询、图表库或用户记录字段。休息功能默认关闭；AI和邮件的可选边界不变。

## 测量方法

2026-11-10，在Windows 11 x64、AMD Ryzen 7 5800H、16逻辑处理器上对照已发布0.8.0与本地0.8.1。两版使用同一个脚本和同一数据生成器，顺序运行，不同时启动两个被测实例。

- 每个场景单独创建新目录：当天3600条合成使用片段、720条空闲区间、40个应用，不读取默认数据库。
- 场景为直接启动到托盘、可见概览且时间线收起、打开后最小化。默认主题与功能开关不变。
- 预热8秒后约25秒每秒采样；窗口由独立实例自行退出。没有锁屏、休眠、修改系统时间或结束用户实例。
- CPU时间是该进程的累计CPU毫秒增量；全机百分比为CPU时间÷墙钟时间÷逻辑处理器数。低占用下一个计时量子的差别就会显著改变百分比。
- 工作集是当前驻留内存，包含可共享页面；私有内存单列，均取采样均值。它们不同于托管堆分配量，不能相互替代。

最终同脚本对照（每格为0.8.0 → 0.8.1）：

| 场景 | 平均工作集 MiB | 平均私有内存 MiB | 进程CPU时间 ms | 平均全机CPU |
| --- | ---: | ---: | ---: | ---: |
| 直接启动到托盘 | 120.57 → 93.70 | 58.11 → 39.15 | 93.750 → 93.750 | 0.0231% → 0.0231% |
| 可见概览，时间线收起 | 165.47 → 150.77 | 106.80 → 93.95 | 2453.125 → 515.625 | 0.6047% → 0.1269% |
| 打开后最小化 | 163.91 → 144.58 | 104.04 → 88.61 | 2046.875 → 78.125 | 0.5043% → 0.0192% |

该次托盘工作集下降约22%，可见概览CPU时间下降约79%，最小化约96%；托盘CPU没有可分辨的改善。打开过窗口后仍保留WPF等资源，因此最小化内存高于直接启动到托盘是正常现象。证据为`artifacts/qa/performance-baseline-final/results.json`及`performance-optimized-final/results.json`。

框架依赖ZIP从0.8.0的约19.88MiB降到0.8.1的约4.41MiB，减少约78%；解压后约5.97MiB，包含程序、使用文档和演示截图，不含.NET桌面运行时。减少的是未使用的跨平台原生库，不能把包体减少比例当作运行内存减少比例。

初轮只有延迟视图/缓冲优化时，可见概览CPU并未改善；据此增加稳定排行行控件复用后才取得上述结果。初轮记录也保留在WORKLOG.md，不将结果差异解释为普适提升比例。

局部托管分配探针：预热后的前台`ReadApp`每次约66888→488字节；含3600个时间片的`DayActivity.Whole`重复读取约389268→0字节。该探针只测当前线程分配，不代表进程全部内存或真实设备的通用数值；全天汇总与小时合计、边界裁剪有独立回归场景。

## 自行复测

在源码目录先运行构建及场景验证，再为每个版本指定自己的EXE：

```powershell
.\scripts\build.ps1 -Test -Publish
.\scripts\measure-resources.ps1 -Exe .\artifacts\release\TraceTime-0.8.1-win-x64\TraceTime.exe -Label local-081
```

脚本使用项目测试程序集生成合成数据库，不需要Python。结果位于`artifacts/qa/performance-<Label>/results.json`；每次创建唯一实例数据目录。保留旧版EXE时可以用不同Label测相同场景。采样期间避免同时编译、截图或运行其他性能测试。

这些是短时受控对照，不能承诺固定CPU或固定内存，也不能证明长期无泄漏。真实数据规模、字体/DPI、打开过的页面、提醒设置、GPU/驱动、系统内存压力均可能改变结果；暂未覆盖多日常驻、数十万时间片和全部DPI/多屏组合。截图上的瞬时资源值包含截图验证工作，不作为性能基准。

## 下一步优先级

1. 先观察真实多日常驻，再决定是否增加更长的回归基准；仅根据可复现的分配或保留对象证据优化。
2. 历史时间片量很大时，可评估只为提醒读取汇总、按需加载原始明细；必须覆盖空闲回扣、跨日、归档/恢复失效及双口径一致性。
3. 若首次托盘驻留仍不满足目标，再评估将提醒/托盘状态从主窗口拆出、延迟创建完整界面。这属于结构调整，应先有目标设备测量和明确预算。

没有把NativeAOT、裁剪或强制内存回收直接应用到现有WPF程序，也没有为追求表面数值牺牲键盘访问、完整记录或提醒准确性。

实现参考：Microsoft的[.NET发布方式](https://learn.microsoft.com/en-us/dotnet/core/deploying/)、[WPF对象性能](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-object-behavior)和[进程路径查询接口](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)。
