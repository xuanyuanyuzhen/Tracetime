# 轻量化设计与资源测量

TraceTime优先保证计时准确、托盘常驻和本地隐私，再减少不需要的计算、分配与文件。本文先记录2026-11-25首批优化，再保留0.8.1与0.8.0的历史对照。

## 2026-11-25：后台提醒只读应用汇总

`CheckLimits`改为调用`GetDaySummary`，省去中断记录查询、时间线对象和时间线排序。汇总与完整日报共用同一聚合实现，仍按Scope合并空闲并裁切时区日界；不增加缓存或持久化汇总表，因此检查点、回扣、删除、恢复和跨日后都直接读取当前记录。可见概览仍使用完整报告，计时及提醒频率保持原样。

对照数据为90天、324000前台片段、64800空闲区间、40应用、40规则。相同SQLite连接上交替运行完整报告与纯汇总，再走提醒选择；每路径预热6次、测量30次，逐tick和应用身份/顺序一致。Windows 11 x64 / .NET 10.0.13：

| 路径 | 中位耗时 ms | p95 ms | 每次平均托管分配 bytes |
| --- | ---: | ---: | ---: |
| 完整日报参考路径 | 39.38 | 46.66 | 2,752,403 |
| 纯汇总提醒路径 | 37.88 | 52.87 | 2,152,859 |

本次可确认每次少分配约599544字节（21.8%）。中位耗时只减少约3.8%，且p95更高，不能据此宣称稳定提速。两种路径仍读取当天3600片段/720空闲，SQL筛选成本并未消失；该比较不是数据库缓存或索引优化的证明，也不是进程内存下降22%的证明。证据：`artifacts/qa/optimization-20261125/summary-90days/summary-benchmark.json`。

复测命令（输出目录必须尚不存在）：

```powershell
./scripts/build.ps1 -Test
./.tools/dotnet/dotnet.exe tests/TraceTime.Tests/bin/Release/net10.0/TraceTime.Tests.dll --measure-summary artifacts/qa/summary-run
./scripts/measure-resources.ps1 -Exe <包目录>/TraceTime.exe -Label local-90days -Days 90 -WithRules -SampleSeconds 10
```

进程脚本的`-Days`默认1，`-WithRules`默认关闭；测量时各状态使用独立合成目录，只有指定后才配置40个不会达到额度的合成规则。逻辑I/O字节来自Windows进程计数器，包含缓存读写及其他进程I/O，不能当成物理磁盘吞吐。进程测量应与构建、截图及其他被测实例分开顺序运行。

最终顺序短测：优化前使用本机已验证的`aoci-review-20261125`包，优化后使用`optimization-20261125`包，均为0.8.2源码阶段。每状态预热8秒、采样约10秒，90天合成数据；旧版六组结束后才启动新版六组。每格为优化前→后：

| 规则数 / 状态 | CPU时间 ms | 平均工作集 MiB | 平均私有内存 MiB |
| --- | ---: | ---: | ---: |
| 0 / 托盘 | 0 → 0 | 92.92 → 109.63 | 39.18 → 54.76 |
| 0 / 概览 | 343.75 → 421.88 | 158.81 → 144.17 | 102.53 → 92.20 |
| 0 / 最小化 | 0 → 0 | 158.27 → 142.61 | 104.22 → 90.21 |
| 40 / 托盘 | 203.12 → 250.00 | 105.40 → 104.58 | 50.71 → 50.38 |
| 40 / 概览 | 1703.12 → 437.50 | 152.75 → 146.93 | 96.99 → 93.33 |
| 40 / 最小化 | 78.12 → 140.62 | 57.48 → 95.97 | 96.26 → 93.99 |

这组结果没有一致的CPU/驻留内存改善方向；未启用规则的路径也有明显波动。10秒采样内实际采集/刷新次数、操作系统工作集回收和桌面状态会影响对照，不把某一行下降归因于本次改动。完整逻辑读写字节在`artifacts/qa/optimization-20261125/resource-comparison.json`，各组证据在`performance-optimization-final-*/results.json`。初轮与构建/包验证重叠的资源数据仅作诊断，未进入此表。本轮已证明的是共享聚合语义等价和托管分配减少，长期常驻收益仍待测。

## 已落实的优化

| 路径 | 0.8.1行为 |
| --- | --- |
| 启动到托盘 | 延迟读取概览和加载应用图标，第一次打开窗口时再加载 |
| 隐藏或最小化 | 暂停概览/规则列表/日历等视图刷新和资源采样；计时、额度检查及休息提醒继续 |
| 每日时间线收起 | 不构造全天图表、小时切片和明细视图；收起后释放这些派生对象的界面引用，展开时恢复完整内容 |
| 概览排行刷新 | 应用顺序未变时复用已有行和控件，只通知改变的值；筛选或排序改变时正常重建 |
| 全天汇总与画刷 | 每个全天快照只生成一次完整汇总；复用固定的冻结调色板画刷 |
| 前台识别 | 复用类名/进程路径缓冲区，遇长路径再扩容；仍按当前前台进程实际查询，不依靠可能复用的PID长期缓存 |
| Windows x64包 | 明确按win-x64发布，仅携带所需SQLite原生库；框架依赖包继续使用已安装的.NET桌面运行时 |

前台事件与1秒兜底采样、常规5秒保存/提醒检查仍保留。没有降低计时采样频率，没有强制GC或裁剪工作集，也没有新增常驻服务、网络轮询、图表库或用户记录字段。休息功能默认关闭；AI和邮件的可选边界不变。

## 测量方法

2026-11-10，在Windows 11 x64、AMD Ryzen 7 5800H、16逻辑处理器上对照已发布0.8.0与本地0.8.1。两版使用同一个脚本和同一数据生成器，顺序运行，不同时启动两个被测实例。

- 每个场景单独创建新目录：当天3600条合成使用片段、720条空闲区间、40个应用，不读取默认数据库。
- 场景为直接启动到托盘、可见概览且时间线收起、打开后最小化。默认主题与功能开关不变。
- 预热8秒后约25秒每秒采样；窗口由独立实例自行退出。没有锁屏、休眠、修改系统时间或结束用户实例。
- CPU时间是该进程的累计CPU毫秒增量；全机百分比为CPU时间÷墙钟时间÷逻辑处理器数。低占用下一个计时量子的差别就会显著改变百分比。
- 工作集是当前驻留内存，包含可共享页面；私有内存单列，均取采样均值。它们不同于托管堆分配量，不能相互替代。

最终同脚本对照（每格为0.8.0 → 0.8.1）：

| 场景 | 平均工作集 MiB | 平均私有内存 MiB | 进程CPU时间 ms | 平均全机CPU |
| --- | ---: | ---: | ---: | ---: |
| 直接启动到托盘 | 120.57 → 93.70 | 58.11 → 39.15 | 93.750 → 93.750 | 0.0231% → 0.0231% |
| 可见概览，时间线收起 | 165.47 → 150.77 | 106.80 → 93.95 | 2453.125 → 515.625 | 0.6047% → 0.1269% |
| 打开后最小化 | 163.91 → 144.58 | 104.04 → 88.61 | 2046.875 → 78.125 | 0.5043% → 0.0192% |

该次托盘工作集下降约22%，可见概览CPU时间下降约79%，最小化约96%；托盘CPU没有可分辨的改善。打开过窗口后仍保留WPF等资源，因此最小化内存高于直接启动到托盘是正常现象。证据为`artifacts/qa/performance-baseline-final/results.json`及`performance-optimized-final/results.json`。

框架依赖ZIP从0.8.0的约19.88MiB降到0.8.1的约4.41MiB，减少约78%；解压后约5.97MiB，包含程序、使用文档和演示截图，不含.NET桌面运行时。减少的是未使用的跨平台原生库，不能把包体减少比例当作运行内存减少比例。

初轮只有延迟视图/缓冲优化时，可见概览CPU并未改善；据此增加稳定排行行控件复用后才取得上述结果。初轮记录也保留在WORKLOG.md，不将结果差异解释为普适提升比例。

局部托管分配探针：预热后的前台`ReadApp`每次约66888→488字节；含3600个时间片的`DayActivity.Whole`重复读取约389268→0字节。该探针只测当前线程分配，不代表进程全部内存或真实设备的通用数值；全天汇总与小时合计、边界裁剪有独立回归场景。

## 自行复测

在源码目录先运行构建及场景验证，再为每个版本指定自己的EXE：

```powershell
.\scripts\build.ps1 -Test -Publish
.\scripts\measure-resources.ps1 -Exe .\artifacts\release\TraceTime-0.8.1-win-x64\TraceTime.exe -Label local-081
```

脚本使用项目测试程序集生成合成数据库，不需要Python。结果位于`artifacts/qa/performance-<Label>/results.json`；每次创建唯一实例数据目录。保留旧版EXE时可以用不同Label测相同场景。采样期间避免同时编译、截图或运行其他性能测试。

这些是短时受控对照，不能承诺固定CPU或固定内存，也不能证明长期无泄漏。真实数据规模、字体/DPI、打开过的页面、提醒设置、GPU/驱动、系统内存压力均可能改变结果；0.8.1这轮未覆盖数十万时间片，2026-11-25补了90天合成数据，仍未覆盖多日常驻和全部DPI/多屏组合。截图上的瞬时资源值包含截图验证工作，不作为性能基准。

## 下一步优先级

1. 先观察真实多日常驻，再决定是否增加更长的回归基准；仅根据可复现的分配或保留对象证据优化。
2. 提醒纯汇总路径已实现并覆盖空闲回扣、跨日、归档/恢复和双口径一致性。若大历史查询耗时仍需改善，先测SQL访问计划和读量，再评估索引或缓存；不直接增加持久化汇总表。
3. 若首次托盘驻留仍不满足目标，再评估将提醒/托盘状态从主窗口拆出、延迟创建完整界面。这属于结构调整，应先有目标设备测量和明确预算。

没有把NativeAOT、裁剪或强制内存回收直接应用到现有WPF程序，也没有为追求表面数值牺牲键盘访问、完整记录或提醒准确性。
